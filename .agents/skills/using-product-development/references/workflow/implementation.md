# 实现阶段

阶段入口：`implementation`

## 1. 阶段目标

根据已确认的需求、设计和实施计划修改源码、测试或配置，并通过与改动风险匹配的验证。

## 2. 阶段流程

```text
确认 Feature 和实现授权
-> 读取需求、方案、计划、状态、变更、测试契约和当前 diff
-> 批判性审查实施计划
-> 建立任务清单
-> 逐任务执行
-> 每任务测试/验证、失败归因和双重内部检查
-> 整体需求与代码质量检查
-> 最终验证
-> 更新控制目录中的 state.md
-> 交付并停止
```

## 3. 进入条件

用户明确要求实现、修复、重构、补测试或按实施计划执行，并且：

- 当前 Feature 目录唯一且已关联已确认的 Work Item 分解结果；
- `requirement.md`、`design.md` 和 `implementation-plan.md` 存在；
- 方案和计划已批准；
- 当前实现范围和用户授权明确。

缺少 `implementation-plan.md` 时停止并要求先进入 `design`。只有用户明确授权无 Feature 的直接修复，才能绕过 Feature 闭环；该任务仍必须遵守事实、风险和验证规则。

## 4. 开始前审查计划

读取 `references/methods/executing-plans.md` 和 `references/shared/test-feedback.md`，然后：

1. 读取完整实施计划并提取所有 Slice、任务和验证记录；
2. 对照控制目录中 `state.md` 的当前任务和活动变更；
3. 检查计划与当前源码、依赖、类型、测试和脚本是否一致，确认每个有用户可观察行为的 Slice 都有测试或替代验证；
4. 发现路径过期、计划缺口、歧义或未批准风险时先停止；
5. 没有问题时建立任务清单并标记第一个任务为 `in-progress`。

## 5. 逐任务执行

实现阶段一次只处理一个已确认 Feature。多 Feature Work Item 必须按依赖和用户授权逐个交付，不能把多个 Feature 的任务合并成一个无边界批次。复杂 Feature 必须按实施计划中的 Slice 执行。每个 Slice 至少声明覆盖的 `requirement-*`、用户可观察结果、修改范围、验证命令、失败停止点和回退方式。一个 Slice 不能依赖一组尚未实现的隐藏前置条件才能验证。

每个 Slice 结束前必须满足：

- 产生可运行或可定向验证的结果；
- 有与 `requirement-*` 对应的验证记录；有用户可观察行为时，自动化测试原则上必须存在；
- 定向验证和受影响回归验证已执行，或记录为 `not-run`/`unavailable` 及原因；
- diff 没有越过当前 Slice 和用户授权范围；
- `state.md` 已记录实际结果、下一 Slice 和恢复信息。

每个任务按以下顺序：

1. 读取任务、`requirement-*`、相关源码事实地图、目标符号和测试；
2. 明确本任务允许创建或修改的源码、测试和配置文件；
3. 能先写测试时，先写失败测试或最小复现；不能先写时，记录替代验证理由；
4. 运行验证，确认失败原因符合预期，并记录验证结果；
5. 做最小实现修改，沿用仓库已有模式；
6. 运行计划指定的定向验证和必要的回归验证；
7. 对照需求、设计、计划和实际行为，按 `test-feedback.md` 归因所有不一致；
8. 检查 diff、类型、调用方、测试质量和计划范围；
9. 进行实现者自检；
10. 进行规范符合性检查；
11. 进行代码质量和范围检查；
12. 两项内部检查都通过后标记任务完成，并更新控制目录中的 `state.md`。

实现者自检不能替代规范检查和代码质量检查。

## 6. 子代理执行

只有用户明确授权多 Agent 且任务相互独立时，才能读取并使用 `references/methods/subagent-development.md`。

每个子代理只接收当前任务、最小状态、源码事实地图、目标文件和验证命令，不传完整聊天历史。不得并行派发会修改同一文件、共享状态或有顺序依赖的实现任务。

子代理返回 `DONE`、`DONE_WITH_CONCERNS`、`NEEDS_CONTEXT` 或 `BLOCKED` 时，按内置方法处理；不得忽略疑虑或强迫同一输入重复失败。

## 7. 风险升级和计划偏离

遇到以下情况停止当前任务并记录：

- 需要修改公共 API、Provider、类型产物、构建或发布脚本；
- 需要跨包或跨业务模块扩大范围；
- 涉及权限、兼容性、迁移、持久化、状态同步或历史能力替换；
- 计划与真实源码冲突；
- 需要增加需求未要求的抽象、配置、扩展点或兜底；
- 验证失败、依赖缺失、指令不清或反复失败。

在控制目录的 `state.md` 记录证据和阻塞，在控制目录的 `change-log.md` 记录需要审批的基线变更。不得边实现边静默修改需求、设计或计划。

发现 Bug 或测试失败时必须先保留复现证据、影响范围和根因分类。实现错误回到当前 `implementation` 任务修复；设计错误回到 `design`；实施计划遗漏文件、依赖、顺序或验证时，暂停并修订 `implementation-plan.md` 后重新确认；需求行为变化回到 `requirement` 并升级基线；测试断言、夹具或前置条件错误才修复测试本身。修复必须补充或执行回归验证，不能通过修改需求、降低断言或删除测试来掩盖实现缺陷。

## 8. 验证边界

实现阶段必须验证。具有用户可观察行为的代码变更原则上必须有自动化测试；配置、构建、发布、迁移和纯文档任务使用匹配的替代验证。至少记录：

- 任务级测试或检查；
- 类型、构建或静态检查；
- 受影响的回归检查；
- 每项验证对应的 `requirement-*`、Slice、命令、预期结果、实际结果和证据路径；
- 未执行或无法执行的关键验证及原因。

关键验证失败或无法执行且用户未接受风险时，不得声明实现完成。

### 测试质量和环境

- 优先验证用户可观察行为、接口契约、状态结果和错误处理，不只验证内部实现细节；
- 按风险覆盖正常、异常、边界、重复请求、失败恢复和受影响回归场景；
- 测试必须能够在行为错误时失败；flaky、超时和环境失败不能标记为 `pass`；
- 测试框架或测试入口缺失时，先建立最小可执行测试 Slice，不能把基础设施缺失当作功能已验证。

## 9. 整体收尾

所有任务完成后：

1. 对照需求和设计做整体规范符合性检查；
2. 检查是否有额外行为、无关改动和计划外偏离；
3. 做整体代码质量检查；
4. 执行与风险匹配的最终验证；
5. 更新控制目录中 `state.md` 的任务、验证、风险和阶段状态；
6. 输出实际修改、任务结果、验证结果和剩余风险。

## 10. 阶段停止

实现完成或阻塞后停止。不得自动进入正式 `review`、独立 `verification`、`release-check`、合入或发布。

## 11. 复杂实现的最小闭环

复杂 Feature 必须先完成一个可运行的最小纵向切片，再扩展剩余场景。每个切片都要在控制目录的 `state.md` 记录：当前任务、已改文件、验证命令、实际结果、下一任务和恢复所需源码事实。禁止一次性修改所有模块后再通过整体运行结果推测问题来源。
