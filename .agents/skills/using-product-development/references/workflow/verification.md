# 验证阶段

阶段入口：`verification`

## 1. 阶段目标

对用户指定的改动、Feature、文件、commit、PR、测试范围或研发产物执行实际验证，输出可复核的证据、未覆盖项和剩余风险。

独立验证阶段不修改功能代码，也不是实现完成后的默认下一阶段。实现阶段内的任务级验证按实现流程执行；独立验证必须重新审查实现者提供的证据，不能只重复其结论。

## 2. 阶段流程

```text
确认验证对象和目标
-> 找到验证依据
-> 读取测试反馈和已有证据
-> 读取真实脚本和配置
-> 建立验证矩阵
-> 按风险执行检查
-> 记录结果和证据
-> 输出未覆盖项与剩余风险
-> 停止
```

## 3. 确认验证目标

先说明要证明什么：

- 需求行为是否满足验收条件；
- 代码、配置、类型、构建或接口是否正确；
- 是否存在回归；
- 性能、安全、权限、兼容性或迁移是否达标；
- 文档、Skill 或规则的路径、引用和关键内容是否一致；
- 发布材料是否具备风险、监控和回滚证据。

对象或目标不明确时停止询问，不直接执行全仓库检查。

## 4. 找到验证依据

验证命令只能来自：

1. `AGENTS.md` 的专项路由和验证矩阵；
2. 当前 Feature 的设计、实施计划和验收条件；
3. `package.json`、`scripts/`、构建配置、测试配置和真实仓库脚本；
4. 用户明确指定的命令或环境。

同时读取 `references/shared/test-feedback.md`，核对实现阶段的验证记录、失败归因、受影响需求和文档版本。

找不到依据时，说明“无专项验证依据”，再根据真实仓库事实选择最小匹配检查。不得编造命令。

## 5. 验证矩阵

按风险建立：

| validation | requirement | Slice | 目标 | 依据/检查命令 | 预期结果 | 实际结果 | 证据 | 独立性 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

状态只能是 `pass`、`fail`、`not-run`、`unavailable`。

## 6. 执行验证

按从快到慢、从局部到整体的顺序：

1. 格式、文档结构和路径检查；
2. 相关单元测试或最小复现；
3. 类型、静态分析和构建；
4. 集成、端到端和回归检查；
5. 高风险任务需要的性能、安全、兼容、迁移或发布演练。

执行前确认工作区、依赖、环境和命令不会修改超出授权范围的数据或代码。

## 7. 结果处理

每项记录验证标识、`requirement-*`、Slice、命令、输入、结果、证据路径、时间和独立性。失败时记录现象、影响范围、失败归因和建议下一步。无法执行时记录原因、替代检查和剩余风险。flaky、超时和环境失败不能写成 `pass`。

验证阶段不为了让结果通过而修代码；需要修复时转入 `implementation` 并重新授权。

## 8. 阶段停止

验证完成、失败或无法继续时停止。不得自动进入实现、评审或发布检查。

## 9. 验证不是单一测试命令

验证结论必须回答“验证了什么”：

- 需求验证：逐条对照当前 Feature 的 `requirement-*` 和验收条件，证明用户可观察行为；
- 实现验证：证明类型、构建、错误处理、状态和接口契约成立；
- 回归验证：证明受影响的既有行为没有破坏；
- 风险验证：按实际影响执行权限、安全、性能、兼容、迁移或恢复检查；
- 研发产物验证：证明文档、Skill、路径、引用和状态字段一致。

只运行编译或少量单元测试，不能自动推出需求、回归和发布风险均已验证。

独立验证至少重新判断预期与实际是否一致，并检查测试是否真的覆盖目标行为；可复用实现阶段证据，但不能把实现者的口头结论或同一条命令的重复输出当作独立结论。

## 10. Work Item 汇总验证

多 Feature Work Item 还必须验证：

- 每个 Feature 的需求、设计、Slice 和验证状态；
- Feature 之间的数据、接口、状态和错误处理契约；
- 总需求的整体验收路径；
- 未交付、部分完成、未执行和不可执行的项目；
- 只有所有必要 Feature 和集成验证满足后，才能报告 Work Item 完成。
- 每个 `requirement-*` 都有通过的验证证据，或有人工批准的未验证风险。

单个 Feature 验证通过不等于总需求完成。
