# 评审阶段

阶段入口：`review`

## 1. 阶段目标

对用户指定的 Work Item、Feature、需求、方案、实施计划、代码 diff、验证结果、发布检查或文档执行独立、只读、基于标准的质量和风险评审。评审对象必须明确作用域，不能用一个 Feature 的评审结论代替多 Feature Work Item 的总体验收。

评审不是实现后的默认下一步，也不负责修复问题。

## 2. 阶段流程

```text
确认评审对象
-> 找到评审标准
-> 读取对象和最小上下文
-> 准备隔离评审包
-> 按标准逐项检查
-> 检查范围和证据
-> 输出按风险排序的问题
-> 停止
```

## 3. 确认评审对象

评审对象必须明确为以下之一或其组合：

- 当前工作区 diff；
- 指定 commit、分支、PR 或补丁；
- 指定文件或目录；
- 指定 Work Item 或 Feature 的需求、方案、实施计划、验证结果或发布检查。

对象不明确时先询问，不做泛泛评审。

## 4. 找到评审标准

按以下顺序寻找标准：

1. `AGENTS.md` 专项路由；
2. 当前阶段产物规范；
3. Feature 的需求、设计、计划和验证矩阵；
4. 代码、架构、接口、权限、安全、测试和文档规范；
5. 用户明确指定的验收口径。

找不到明确标准时，必须标注“基于通用风险判断”，不得伪造依据。

## 5. 准备隔离评审包

优先使用新会话或新 Agent。评审包只包含：

- 评审对象、路径、diff 或文档；
- 相关需求、方案、计划和变更条目；
- 适用标准；
- 从标准提取的检查项；
- 已执行、未执行和无法执行的验证；
- 要重点检查的风险范围。

不得传入完整聊天历史，不得把实现者的解释当成事实。无法隔离时，标注“同上下文复核，仅作辅助判断”。多 Agent 评审必须先获用户确认。

## 6. 按对象检查

### Work Item/需求评审

- Work Item 是否完成复杂度判断、Feature 拆分或合并理由和用户确认；
- Feature 清单、依赖、需求映射、跨 Feature 契约和整体验收是否完整；
- 每个 Feature 是否只包含一个独立交付边界；
- 每个 `requirement-*` 是否只表达一个可验证行为，是否错误使用 `REQ-*` 或纯编号；
- 测试或替代验证是否真正覆盖用户行为、异常和边界，而不是只验证内部实现；
- 测试失败、环境失败和文档不一致是否完成归因，是否存在通过降低断言规避问题的情况；

- 目标、范围、非目标和用户是否清楚；
- 功能、规则、异常、边界和验收条件是否完整；
- 需求之间是否矛盾；
- 是否把技术方案写成需求事实；
- 待确认项是否影响后续设计。

### 方案评审

- 多 Feature 任务是否每个 Feature 都有独立的 `design.md` 和 `implementation-plan.md`；
- 方案是否越过当前 Feature 边界，跨 Feature 依赖是否回到总需求层记录；

- 是否覆盖每条需求；
- 架构、模块、接口、类型、数据和状态是否一致；
- 调用链、异常、重试、权限、性能和兼容性是否合理；
- 备选方案和取舍是否有依据；
- 方案是否与真实源码和脚本相符；
- 是否有可行性证据、验证、监控和回滚方案。
- 可测试性、测试数据、可观测结果和验证限制是否在方案中明确；

### 实施计划评审

- 每个需求是否有任务；
- 文件、符号、依赖和顺序是否明确；
- 每个任务是否有验证命令和预期结果；
- 是否有占位内容、隐藏依赖或未定义符号；
- 任务粒度是否适合独立实现和验证。
- 每个 Slice 是否有测试范围、预期结果、验证记录和失败停止点；

### 代码评审

- 是否符合需求和已确认设计；
- 是否有逻辑、类型、错误处理、状态和兼容性问题；
- 是否有无关改动、未授权扩展或范围漂移；
- 测试是否覆盖新增和回归风险；
- 是否留下未验证的关键行为。

### 验证和发布材料评审

- 证据是否对应目标和风险；
- 是否把未执行或静态判断写成通过；
- 发布范围、监控、灰度和回滚是否完整；
- 人工确认项是否被明确列出。

### 总需求汇总评审

- 所有必要 Feature 是否分别完成需求、设计、实施、验证和发布检查；
- 跨 Feature 契约是否有集成验证证据；
- 是否把未交付、部分完成、未执行或无法执行项错误报告为整体完成。

## 7. 输出

先输出问题，再输出补充说明。每个问题说明严重级别、位置、事实依据、影响和建议。区分：

- 已验证存在的问题；
- 基于材料判断的风险；
- 表达不清或不推荐的写法。

评审建议不得自动变成修改动作。

## 8. 评审类型和边界

评审对象决定检查内容，不得笼统地说“评审研发质量”：

- **需求评审**：评审目标、范围、规则、异常和验收，不评判代码实现；
- **方案评审**：评审架构、调用链、数据/状态、风险、验证和回滚，不修改方案；
- **计划评审**：评审任务是否能被逐项执行和验证，不替实现者补任务；
- **代码评审**：评审当前 diff 是否符合需求、方案、规范和质量要求，不把未执行测试写成通过；
- **验证材料评审**：评审证据是否真实、完整、对应风险，不代替执行验证；
- **发布评审**：评审发布范围、运行风险、监控、灰度和回滚，不代替负责人批准发布。

用户未指定对象时，先询问评审“什么材料”，再决定读取范围。

## 9. 阶段停止

评审结论输出后停止。需要修改时，等待用户授权进入 `implementation` 或 `documentation`。
