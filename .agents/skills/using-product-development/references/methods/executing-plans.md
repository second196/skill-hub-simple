# 实施计划执行方法

本方法用于 `implementation` 阶段。它内置计划审查、任务清单、逐任务执行、验证检查点和阻塞处理，不要求外部 Superpowers。

## 1. 开始前审查

1. 读取完整 `implementation-plan.md`，提取所有任务和任务上下文；
2. 读取正式的 `requirement.md`、`design.md`，以及 `.product-development` 控制目录中的 `state.md` 和当前 diff；
3. 检查计划是否仍与源码事实、依赖和当前工作区一致；
4. 找出疑问、缺口、过期路径、未批准风险和范围冲突；
5. 有问题先向用户说明，不能带着关键疑问开始实现；
6. 无问题时建立任务清单，记录每个任务的状态。

## 2. 逐任务循环

对每个任务依次执行：

1. 将任务标为 `in-progress`；
2. 只读取该任务、源码事实地图中的相关条目、目标符号和相关测试；
3. 必要时先写失败测试或最小复现；
4. 做最小实现修改；
5. 执行计划指定的验证命令；
6. 检查 diff 是否只覆盖当前任务和授权范围；
7. 做实现者自检；
8. 完成内部规范符合性检查和代码质量检查；
9. 两项检查都通过后，将任务标为 `completed`，更新控制目录中的 `state.md`；
10. 再进入下一个任务。

不能并行修改相互依赖的任务。并行只适用于明确互不共享文件、状态和依赖的只读检查。

## 3. 批次和检查点

默认一次只执行一个任务。只有用户明确授权连续执行，且任务之间没有人工确认门、没有公共契约变化、没有共享文件冲突时，才允许把多个任务组成一个小批次；批次最多覆盖一个可独立验证的纵向切片。每个批次结束仍必须：

1. 运行该批次的验证；
2. 检查工作区 diff 和任务范围；
3. 更新控制目录中 `state.md` 的任务、验证和恢复信息；
4. 报告结果并确认是否继续。

上下文即将压缩、切换会话或主 Agent 失去当前任务细节时，必须先停在检查点，不能在未记录任务状态的情况下继续。

## 4. 计划之外的情况

遇到以下情况立即停止当前任务：

- 缺少依赖或环境无法复现；
- 指令不清或存在两种行为解释；
- 计划有关键缺口；
- 测试失败且原因不是预期中的红灯；
- 验证反复失败；
- 需要扩大文件、模块或包范围；
- 需要修改公共契约、迁移、权限或兼容性；
- 真实源码与计划冲突。

把阻塞记录到控制目录中的 `state.md`，标明已完成修改、已执行验证、阻塞任务和需要用户决定的事项。不要强行重试相同方案。

## 5. 任务状态处理

如果使用隔离子代理，要求其返回以下状态之一：

- `DONE`：完成并通过自检，进入规范检查；
- `DONE_WITH_CONCERNS`：完成但有疑虑，先读取疑虑并处理；
- `NEEDS_CONTEXT`：缺少上下文，补充最小信息后重新派发；
- `BLOCKED`：评估是上下文不足、推理能力不足、任务过大还是计划错误，再采取对应动作。

不得忽略 `NEEDS_CONTEXT` 或 `BLOCKED`，不得在输入不变时强迫同一 Agent 重试。

## 6. 实现后的双重检查

所有任务修改完成后必须分别执行两次检查，检查者依据材料而不是实现者口头说明：

### 规范符合性检查

- 每条已批准需求是否都有对应行为；
- 是否严格遵守设计中的接口、类型、状态和错误约束；
- 是否遗漏异常、边界、权限、兼容和回滚要求；
- 是否增加了需求没有批准的行为或文件；
- 测试是否验证了需求而不是只验证内部实现。

### 代码质量检查

- 是否存在逻辑、类型、资源、并发、错误传播或安全问题；
- 是否复用了仓库已有模式，是否引入不必要抽象；
- 是否有死代码、重复逻辑、脆弱测试或无关格式化；
- 是否能解释每个修改文件和每条验证结果。

任一检查失败都回到当前任务修复并重新验证，不能把问题留给正式评审阶段再处理。

## 7. 完成收尾

所有任务完成并通过检查后：

1. 做一次整体需求符合性检查；
2. 做一次整体代码质量和范围检查；
3. 执行与改动风险匹配的最终验证；
4. 更新控制目录中 `state.md` 的任务、验证和剩余风险；
5. 输出实现交付说明并停止。

除非用户另行要求，不自动提交、合入、发布或执行分支收尾。
