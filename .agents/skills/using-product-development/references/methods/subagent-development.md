# 子代理开发方法

本方法只在用户明确授权多 Agent 后使用。它适用于已有实施计划且任务相互独立的实现，不适用于强耦合、需要持续整体判断或会同时修改相同文件的任务。

## 1. 选择条件

使用前确认：

- 计划已经批准；
- 任务可以独立执行；
- 每个任务的输入、输出和验证明确；
- 用户已经允许多 Agent；
- 平台能隔离 Agent 上下文；
- 没有并行写同一文件或共享状态的风险。

如果任务强耦合，使用主 Agent 按 `executing-plans.md` 执行。

## 2. 最小任务包

每个实现 Agent 只接收当前 Work Item/Feature 下的一个 Slice 或一个任务，并只接收：

- 完整的当前任务文本；
- 该 Slice/任务覆盖的语义化 `requirement-*`；
- 相关 `state.md` 决策和源码事实地图条目；
- 目标文件、符号和现有模式；
- 相关测试、真实命令和预期结果；
- `references/shared/test-feedback.md` 要求的验证记录和失败归因方式；
- 禁止扩大范围的说明。

不得传入完整聊天历史，不得把实现者的解释当作事实，不得要求 Agent 自己从大计划中重新寻找任务。

## 3. 每个任务的执行循环

1. 派发一个实现 Agent；
2. Agent 有问题时，主 Agent 先回答或向用户确认，再继续；
3. Agent 实现、测试并进行自检，返回验证命令、实际结果和证据；
4. 派发规范符合性检查，确认实现没有漏做、越界或增加未要求行为；
5. 若不通过，回给同一任务修复，再重新检查；
6. 规范检查通过后，派发代码质量检查；
7. 若不通过，修复后重新检查；
8. 两项检查通过后才标记任务完成。

不得跳过任一检查，也不得在规范检查通过前开始代码质量检查。

## 4. 子代理交接协议

主 Agent 派发前记录任务包编号、输入版本、目标文件和预期验证。子代理返回时必须报告：

- 实际修改的文件和符号；
- 实际执行的命令及结果；
- 未执行或无法执行的检查；
- 与计划不一致的地方；
- 剩余风险和需要主 Agent 决定的事项。

主 Agent 只把返回内容当作待核对信息，必须重新检查工作区 diff、关键验证结果和需求/设计/计划一致性。子代理不能自行修改需求、设计、计划、发布配置或共享状态；发现需要扩大范围或无法判断失败归因时返回 `BLOCKED`。

## 5. 任务和模型选择

- 机械的单文件任务可以使用较快模型；
- 多文件集成、调试和模式匹配使用常规模型；
- 架构、复杂方案和最终整体评审使用能力最强的可用模型。

模型名称由当前平台决定，不在 Skill 中编造固定模型名。

## 6. 全部任务完成

所有任务完成后，再做一次整体规范符合性检查和整体代码质量检查。子代理内部检查不等于用户明确要求的正式 `review` 阶段；如果用户没有请求正式评审，完成内部检查后回到实现阶段交付并停止。
