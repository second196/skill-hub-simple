# 实施计划编写方法

本方法用于 `design` 阶段，在用户接受方案后编写当前 Feature 的 `implementation-plan.md`。计划必须来自已确认的 Work Item 分解和当前 Feature 边界，是后续实现的唯一执行依据之一，不能只是任务标题列表。

## 1. 计划输入

读取并核对：

- 已确认的 `requirement.md`；
- Work Item 的 `decomposition.md`、Feature 清单和当前 Feature 的需求映射；
- 已确认的 `design.md`；
- `.product-development` 控制目录中 `state.md` 的源码事实地图和决策；
- 相关源码、类型、入口、测试和真实验证脚本；
- 控制目录中 `change-log.md` 的已批准有效变更。

如果方案、源码和需求冲突，停止编写计划并提出冲突，不得自行选择。

## 2. 先锁定文件结构

先列出创建、修改、测试和需要检查的文件，并说明每个文件职责。对于已有大文件，遵循现有模式，不因计划方便而擅自重构；只有大文件阻碍本次目标时才把拆分列为明确任务。

在列文件前先做一次“事实到文件”的映射：入口、核心逻辑、持久化/状态、错误出口、测试入口、配置和文档分别落在哪个真实路径。查不到的路径必须记为未知并停止计划编写，不能使用类似命名文件替代。

## 3. 任务粒度

每个 Slice 应能形成可运行或可定向验证的最小纵向闭环，每个任务应能独立理解、修改和验证。优先拆成短步骤：

1. 写出失败测试或最小可验证条件；
2. 运行验证，确认失败原因符合预期；
3. 写最小实现；
4. 运行验证，确认通过；
5. 检查 diff 和任务范围。

任务不必机械限制为固定分钟数；应以能够在一个小上下文中完成和验证为准。强耦合任务不要为了追求小粒度而拆成不可独立执行的碎片。

复杂 Feature 优先采用“可运行的最小纵向切片”顺序：先打通一个最小正常流程，再补异常/边界，再补跨模块能力，最后处理迁移、兼容、性能和发布支持。每个切片结束时都应有可执行的验证，而不是先堆积所有代码再统一调试。

## 4. 每个任务的固定格式

```markdown
### Task N：任务名称

Slice：slice-<meaningful-result>
需求：requirement-<semantic-name>
依赖：Task N-1 或无
文件：Create / Modify / Test 的精确路径和符号
目标：本任务完成后的行为
实现：具体逻辑、接口、类型或数据变化
验证：精确命令、输入和预期结果
停止条件：失败时停止在哪里
回滚：本任务如何撤销或恢复
```

代码步骤必须给出足够的实现细节，不能写“适当处理异常”“补充测试”“类似上一个任务”等占位语句。必要时给出签名、关键分支、数据样例或伪代码；避免把整个项目源码复制进计划。

## 5. 计划自检

计划完成后，从头对照需求和方案检查：

- 每个需求是否至少对应一个任务，或明确说明无需代码任务；
- 需求覆盖矩阵和任务中的 ID、类型、方法名是否一致；
- 文件路径、符号、字段和签名是否前后一致；
- 是否包含正常、异常、边界、兼容和验证任务；
- 是否存在 TODO、TBD、未定义方法或隐含依赖；
- 是否出现需求之外的功能、抽象或配置；
- 任务顺序是否能从空状态逐步得到可运行结果。

发现缺口就修改计划并重新自检。计划写入当前 Feature 后停止，不能自动进入实现。

## 6. 计划质量门

计划只有同时满足以下条件才能请求用户确认：

- 任务按依赖排序，前一个任务的产物是后一个任务的明确输入；
- 每个 `requirement-*` 至少出现在一个任务和一个验证项中；
- 每个 Slice 都有明确用户结果、范围、依赖、验证和失败停止点；
- 每个高风险假设都对应源码事实、实验、测试或明确的人工确认；
- 每个可能失败的外部调用、状态变化和数据写入都有失败处理；
- 任务失败时能定位到单个任务，不需要回滚整批无关修改；
- 计划中没有“后续再看”“适当处理”“补充测试”等不可执行表述。
