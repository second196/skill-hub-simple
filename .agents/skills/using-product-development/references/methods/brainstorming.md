# 头脑风暴方法

本方法用于 `requirement` 和 `design` 阶段的互动澄清与方案探索。它不是独立阶段，不得改变当前阶段的产物、路径、写入权限或停止条件。

## 1. 适用范围

- 需求存在歧义、缺少边界或验收口径；
- 需求包含多个独立子系统；
- 存在两条以上明显可行的技术路径；
- 需要识别异常、依赖、影响面或关键假设；
- 需要在实现前获得用户对方案和取舍的确认。

简单且完整的请求可以缩短为几句话，但不得跳过事实确认和出口检查。

## 2. 执行步骤

### 步骤 1：了解项目上下文

先检查最小必要范围：仓库结构、相关文档、近期相关 diff、入口文件、调用方、测试和真实脚本。不要先读取整个仓库。

### 步骤 2：判断规模

如果用户一次提出聊天、文件存储、计费、分析等多个相对独立的子系统，立即指出需要拆分。列出子项目关系和建议顺序，先为第一个子项目完成正常流程。

### 步骤 3：一次问一个问题

每条消息最多问一个改变范围、行为、约束或验收标准的关键问题。能使用互斥选项时优先提供选项，但不要用选项掩盖缺失信息。

问题顺序优先为：真实目标、使用者、范围、非目标、成功标准、约束、依赖、异常、兼容性和风险接受方式。

### 步骤 4：提出备选方案

理解目标后，提出两到三个可行方案，说明：

- 方案如何满足需求；
- 需要改动的模块和契约；
- 优点、缺点、成本和风险；
- 适用条件；
- 推荐哪一个以及原因。

不要把探索中的可能性写成已确认事实。

### 步骤 5：分段展示方案

按复杂度分段展示：架构、组件边界、数据流、状态变化、错误处理、测试和发布影响。每个关键段落后确认用户是否理解并接受，不要一次塞入整篇方案。

### 步骤 6：获取确认

方案确认前只能输出草稿、问题和待确认项。用户确认的是需求口径、方案取舍、范围和风险接受，不等于授权修改代码。

### 步骤 7：结束并固化

确认后立即把结论转成稳定记录：

- 需求阶段写入语义化 `requirement-*`、验收条件、非目标和待确认项；
- 方案阶段写入决策编号、被否决方案、源码事实、风险和可行性证据；
- 每条记录标明 `confirmed`、`assumption` 或 `needs-confirmation`；
- 更新 `.product-development` 控制目录中的 `state.md`，必要时追加 `change-log.md` 后才结束本轮。

头脑风暴不会直接产生代码，也不会因为讨论结束就自动进入实现。若用户只要求讨论，结论保持在对话草稿中；若用户要求写正式产物，仍需经过对应阶段的确认门。

## 3. 自检

正式写入前检查：

1. 是否有 TBD、TODO、模糊需求或未完成章节；
2. 各章节是否互相矛盾；
3. 方案是否大到需要拆成多个 Feature；
4. 同一句需求是否可能被两种方式理解；
5. 是否把推荐、假设和确认事实混在一起；
6. 每个需求是否有方案响应、计划任务和验证方式。

发现问题就在当前草稿中修正，再交给用户确认。不要写入外部默认设计路径，也不要自动调用计划或实现流程。

## 4. 复杂需求的额外规则

当需求包含三个以上独立业务目标、多个入口、跨包调用、数据迁移、权限变化或不明确的异常策略时，视为复杂需求。此时必须：

1. 先建立子目标清单和依赖关系；
2. 为每个子目标分配语义化 `requirement-*`，不得用一段长文字或纯编号代替；
3. 为每个正常流程至少补一个异常和一个边界场景；
4. 明确哪些事实需要查源码，哪些需要用户确认，哪些需要实验验证；
5. 不把所有子目标压进一个无法独立验收的 Feature。
