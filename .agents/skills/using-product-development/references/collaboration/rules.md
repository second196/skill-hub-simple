# 协作规则

## 1. 优先级

发生冲突时依次服从：

1. 用户本次明确要求；
2. `AGENTS.md`；
3. 本协作规则；
4. 命中的仓库专项规范；
5. 当前阶段流程；
6. 内置执行方法。

任何方法都不得覆盖阶段边界、文件权限、产物路径、验证门禁和人工确认。

## 2. 事实与上下文

- 先确认真实路径、入口、调用方、类型、脚本、测试和相邻模式。
- 不把历史聊天、压缩摘要、实现者解释或通用经验当成仓库事实。
- 只读取当前阶段和当前任务需要的源码；用源码事实地图保存结论，不把大段源码复制到 `.product-development` 控制目录的 `state.md`。
- 跨会话或上下文压缩后，重新读取控制目录中的 `state.md`、当前阶段产物和当前 diff。

## 3. 范围

- 每一项修改都必须能追溯到需求 ID、变更 ID 或用户本次明确请求。
- 不做无关重构、迁移、格式化、命名调整或历史清理。
- 不新增需求未要求的配置、扩展点、抽象层、兜底逻辑和兼容分支。
- 发现无关问题可以报告，不得顺手修复。

## 4. 人工确认

以下事项必须等待用户确认：

- 需求取舍和范围变化；
- 公共 API、公共导出、类型契约、Provider、构建或发布脚本变化；
- 权限、安全、数据持久化、状态同步、迁移和兼容性风险；
- 跨多个包或业务模块扩大范围；
- 跳过关键验证；
- 启用多 Agent；
- commit、合入、发布和回滚。

## 5. 验证诚信

验证命令只能来自真实仓库脚本、专项规范、验证矩阵或用户指定方式。结果必须区分：

- 已执行并通过；
- 已执行但失败；
- 未执行；
- 无法执行。

静态阅读、推断、未执行和无法执行不得写成“已通过”。

## 6. 写入规则

- 用户说“只分析”“只评审”“先不要改”时不得修改文件。
- 正式需求、方案和计划写入前必须完成对应确认门。
- 后续微调默认记录为增量变更，不自动重写历史基线。
- 未经用户同意不得自动提交、合入、发布或向远端发送代码。

## 7. 交付

每次交付至少说明当前阶段、Feature、完成内容、修改文件、依据、已执行验证、未执行验证、剩余风险和停止原因。
