## 3. 功能描述

### 3.1 功能目标与范围

平台应为公司内部 Skill 提供统一的登记、发现、版本管理、授权范围发布、审核、下线、撤回和审计能力。首期为公司私有化部署，仅服务公司内部员工，不建设 SaaS 多租户能力。

本 Feature 不负责 Agent runtime 执行、运行时 Tracker 采集、评测 Runner 执行或 Skill 内容的自动生成；它向其他 Feature 提供不可变版本、发布范围、发布门禁和治理审计结果。

### 3.2 原子需求清单

#### `requirement-skill-asset-registration`

有权限的用户应能注册或导入 Skill，并查看来源类型、来源定位、导入结果和失败原因。导入内容不可访问、无法读取或缺少必要内容时，系统必须失败并阻止生成可发布版本。

验收条件：成功资产可追溯到来源；失败结果包含原因；缺少必要内容的资产不能进入发布流程。

#### `requirement-skill-metadata-completeness`

系统应展示 Skill 主描述、附属内容、名称、描述、来源、许可、依赖和适用运行时的完整性。未知或缺失信息必须显式标记，不得由平台猜测补全。

验收条件：资产详情可查看内容清单和元数据检查结果；缺失项和未知项可定位。

#### `requirement-skill-catalog-search`

用户应能在授权范围内按名称、描述、标签、来源、适用运行时、状态和版本浏览和搜索 Skill，并查看版本、发布、评测和安装关联信息。

验收条件：用户能区分不同版本和生命周期状态，并进入指定版本详情。

#### `requirement-skill-version-immutability`

每次 Skill 内容变更都必须生成独立版本。已创建版本的内容、来源和内容标识不得原地修改，用户应能查看不同版本之间的差异。

验收条件：修改已创建版本会得到新版本；历史版本内容和来源保持不变；版本差异可查询。

#### `requirement-skill-lifecycle-state`

平台至少应区分草稿、候选、已发布、已下线、紧急撤回和已废弃状态，并记录状态变化、原因和操作主体。不可分发状态不得作为默认安装版本。

验收条件：不同状态对查看、安装和发布的影响可见；已下线或已废弃版本不能被误当作最新可安装版本。

#### `requirement-skill-release-scope`

平台应支持在公司、项目和环境等授权范围内发布版本，并展示发布目标、当前版本、发布时间和范围。一个版本可以发布到一个或多个授权范围。

验收条件：用户能查询指定版本发布到哪些范围，以及每个范围当前使用的版本。

#### `requirement-skill-release-gate`

发布前必须关联静态扫描、受控评测、审核、风险判断和灰度证据。扫描失败或任一必需证据缺失时必须阻止发布并说明原因；高风险候选不得绕过人工审核。

发布策略必须可按公司、项目和环境配置，并记录策略版本。默认策略为：低风险白名单候选才允许自动发布；无高危或严重安全问题、无权限或外部写操作变化、无新运行时兼容性变化，至少完成 30 个有效评测案例，回归结果和有效评分不低于基线。其他候选进入人工审批。

验收条件：门禁缺失时发布被阻断；符合白名单的候选可按当前策略发布；系统能展示命中的策略版本和全部门禁证据。

#### `requirement-skill-governance-audit`

平台应按授权范围和角色控制导入、版本创建、发布、下线、紧急撤回、安装、运行数据查看、评测执行和治理配置。关键操作必须记录主体、时间、对象、前后状态、原因和生效范围。人工申请人与审批人必须分离；自动发布主体不得伪装为人工审批人。

验收条件：未授权用户无法执行关键操作；审计记录可以还原完整状态变化。

#### `requirement-skill-data-retention`

数据保留策略必须可配置、可按授权范围生效、可设置生效时间并记录策略版本。默认采用分层策略：Skill 制品、不可变版本、评测报告、发布决策和审计数据永久保留；原始运行事件默认保留 365 天；聚合指标默认保留永久。调整或缩短保留期必须由有权限的治理人员执行并审计，不提供用户临时删除单条数据的能力。

验收条件：管理员能查看和调整策略；新策略的生效范围和时间可查询；系统不会无审计地自动删除或被普通用户直接删除数据。

### 3.3 异常与边界

- 导入或版本内容无法读取时必须失败，不生成可发布对象。
- 版本缺少可追溯来源、评测或扫描证据时保持不可发布状态。
- 发布策略不可用、配置版本不存在或策略条件无法判断时默认阻止发布，不采用隐式放行。
- 普通下线默认只阻止新增安装；已安装实例是否停用由安装与回退 Feature 的更新、回退或紧急撤回流程处理。
- 高危安全问题可触发紧急撤回，但必须记录影响范围和执行结果。

### 3.4 可配置项与默认值

| 配置项 | 默认值 | 调整约束 |
| --- | --- | --- |
| 发布范围层级 | 公司、项目、环境 | 仅治理管理员可调整，按范围隔离 |
| 自动发布白名单 | 低风险且满足全部门禁的候选 | 策略版本化并记录命中规则 |
| 有效评测案例数 | 至少 30 个 | 不能低于组织规定的最低门槛 |
| 数据保留策略 | 制品/评测/审计永久；原始运行事件 365 天；聚合指标永久 | 调整需授权、生效时间和审计 |

### 3.5 首期默认账户

首期部署必须提供两个可登录的默认账户：系统管理员账户 `admin` 和普通用户账户 `user`。默认密码分别为 `admin123` 和 `user123`；密码只能以 BCrypt 哈希形式持久化，默认账户初始化必须幂等，不能在后续启动或迁移时覆盖已修改的密码。

验收条件：`admin/admin123` 和 `user/user123` 均可通过账户密码登录并创建服务端 Session；`admin` 具备系统治理范围内的管理员权限，`user` 仅具备普通资产使用权限。

### 3.6 参考项目对齐增量需求

#### `requirement-skill-package-content`

有权限的用户应能导入包含多个文件的 Skill 包，并查看文件路径、文件类型、大小、读取状态和完整性结果。导入必须保留包内文件结构；缺少主描述文件、存在不可读取文件或包含非法路径时，导入失败且不能生成可发布版本。

验收条件：用户可以上传一个真实 Skill 包并查看文件清单；失败包显示明确原因且不出现在可发布目录中；成功包可以按文件查看内容或下载完整包。

#### `requirement-skill-semantic-version-tags`

Skill 版本应支持语义化版本号和组织自定义标签。用户可以查看 `latest`、`stable`、`beta` 等标签指向的具体版本；标签变更必须保留历史记录，标签不能指向不可分发状态的版本。

验收条件：版本号格式错误时不能发布；标签解析结果始终对应具体 `version_digest`；下线、撤回或废弃版本不能继续作为可安装标签目标。

#### `requirement-skill-discovery-search`

用户应能在授权范围内通过独立的 Skill 发现入口，按名称、命名空间、描述、标签、版本、状态、更新时间和使用情况搜索，并使用稳定的排序和分页浏览结果。

验收条件：搜索结果可进入 Skill 详情；无权限的命名空间和资产不出现在结果中；空结果、加载失败和索引延迟均有明确界面状态。

#### `requirement-skill-file-browse-download`

用户应能在 Skill 版本详情中浏览文件目录、查看文本文件内容、下载单文件和下载指定版本包。文件路径必须安全处理，越权版本和不存在文件不得返回内容。

验收条件：文件浏览、文本预览和版本包下载均关联明确的 `version_digest`；二进制或过大的文件显示不可预览并仍可按权限下载；非法路径请求被拒绝。

#### `requirement-skill-version-comparison`

用户应能选择同一 Skill 的两个具体版本进行比较，查看版本元数据变化、文件新增/删除/修改和文本差异。比较结果必须明确两侧版本，不能使用未确定的 `latest` 代替版本。

验收条件：版本比较页面可从版本详情进入；不存在的版本、跨资产版本和无权限版本比较被拒绝；历史版本内容不因比较操作改变。

#### `requirement-skill-publish-review-lifecycle`

发布人应能提交候选版本审核，审核人应能查看版本内容、门禁证据和风险信息并执行通过、拒绝、撤回或重新发布。版本发布、归档、恢复和下线等操作应在页面中展示当前状态、原因和操作主体，并遵循审批人分离。

验收条件：申请人不能审批自己的申请；必需证据缺失时不能发布；拒绝、撤回和归档结果可查询；恢复操作不能绕过门禁产生已发布版本。

#### `requirement-skill-namespace-governance`

系统管理员和命名空间所有者应能管理命名空间、成员和成员角色。命名空间至少支持 Owner、Admin、Member 三类角色，并将资产、发布和审核权限限制在命名空间和组织范围内。

验收条件：成员可以查看自己被授权的命名空间；Owner/Admin 可以按权限增删成员或调整角色；Member 不能修改命名空间治理设置；离开命名空间后不能继续访问受限资产。

#### `requirement-governance-account-management`

系统管理员应能查询、启用或停用普通账户并查看账户的角色和授权范围；普通用户不能管理账户、角色或范围授权。停用账户不能新建会话，已有会话在下一次鉴权时失效。

验收条件：管理员账户管理操作有审计；停用账户不能登录或执行治理操作；普通用户访问账户管理入口被拒绝。

#### `requirement-skill-governance-console-branding`

治理控制台应提供与参考项目相近的发现、列表、详情、版本和治理工作台信息架构，所有用户可见文案使用中文。界面主题应采用公司品牌蓝色体系，品牌色、状态色、间距和字体应统一，且在桌面和移动宽度下保持内容可读、操作可达。

验收条件：主要流程可以从发现/资产目录进入详情、版本、发布和治理操作；页面不存在中英文混排的功能文案；品牌色集中管理，后续可以调整而不改变业务行为。

### 3.7 增量范围和明确排除

本次增量只对齐参考项目中与账户治理、Skill 资产发现、版本内容和发布治理直接相关的能力。继续排除 OAuth2、统一单点登录、CLI Device Flow、API Token、S3、微服务拆分、收藏、评分、订阅和通知；安装执行、运行事件采集和评测 Runner 仍由既有 Feature 负责。

## 4. 非功能性需求

| 类型 | 要求 | 说明 |
| --- | --- | --- |
| 可追溯性 | 版本、来源、发布范围、门禁证据和审计记录可关联 | 关联缺失时显示缺失原因 |
| 数据完整性 | 已创建版本不可原地修改 | 使用新版本承载变化 |
| 安全 | 关键操作遵循最小权限和审批人分离 | 高风险操作必须人工审核 |
| 可配置性 | 发布和保留策略支持范围化、版本化和后期调整 | 调整本身必须审计 |

## 6. CR-017 API Token 增量需求

> 当前增量需求版本：v4。以下内容覆盖原 v3 中“API Token”排除项；OAuth2、统一单点登录、CLI Device Flow、S3、微服务和其它排除项继续有效。

### `requirement-skill-api-token-access`

系统应支持账户自主创建和管理 API Token，并允许自动化客户端使用 `Authorization: Bearer <token>` 调用 Skill 资产读取和 ZIP 包导入接口。Token 必须以 `sk_` 前缀生成，服务端只保存不可逆 SHA-256 摘要，不保存原文；完整 Token 只在创建成功响应中返回一次。

Token 至少支持名称、作用域、创建时间、过期时间、最后使用时间和撤销状态。作用域至少包括 `skill:read`、`skill:publish`、`token:manage`：读取作用域覆盖既有资产目录、资产详情、版本、文件和制品下载接口；发布作用域覆盖既有 Skill ZIP 导入接口；管理作用域覆盖 Token 的查询、创建、过期时间更新和撤销接口。网页端继续使用账户密码、服务端 Session 和 CSRF；Bearer API 请求不改变网页 Session 流程。

验收条件：

- 登录用户可以在控制台创建、查看、修改过期时间和撤销自己的 Token；列表和详情不返回完整 Token。
- 创建响应只返回一次完整 Token，刷新或再次查询不能恢复原文；过期或撤销 Token 返回 401。
- Bearer Token 只能访问其拥有作用域的接口；缺少作用域返回 403；无 Bearer 认证返回 401。
- `skill:read` 可以调用既有资产读取接口，`skill:publish` 可以调用既有 ZIP 导入接口；Token 身份仍受账号启停和资产范围权限约束。
- Token 管理操作记录主体、Token 标识、作用域变化和撤销/过期原因；日志和错误响应不得泄露 Token 原文。

### 明确排除

- 本增量暂不实现 CLI、Token 本地凭据文件、设备授权流程、OAuth2 或统一单点登录。
- Token 不写入 Skill 包、项目目录或数据库明文；Token 不负责压缩 Skill，客户端或调用方负责准备 ZIP 包，服务端继续负责解压、校验和导入治理。
