## 2. 需求来源

来源：用户补充的公司级 Skill 集中管理平台定位与 `docs/research/skill-hub-research.md` 调研报告。

## 3. 功能描述

### 3.1 产品目标与范围

SKILL HUB 是公司内部集中管理 Skill 资产的平台，首期采用公司私有化部署，仅服务公司内部员工，不提供 SaaS，也不建设多租户能力。平台应让公司能够统一登记、发现、分发、发布、下线和维护 Skill，并持续收集 Skill 在实际 Agent 运行中的使用与质量证据，支持基于证据形成新版本。

平台覆盖以下闭环：

```text
注册或导入 Skill -> 检查与版本化 -> 评测与审核 -> 发布
-> 从平台获取 Skill + 安装 skill-tracker -> 运行数据回传
-> 观测、评测和问题归因 -> 形成进化候选版本
-> 复测、审核、灰度 -> 发布新版本或回退
```

本 Feature 的核心交付对象是 Skill 资产及其版本、发布和安装实例的统一管理，以及与之关联的 Tracker 数据、评测证据和进化记录。平台不替代 Agent runtime，不替代通用日志或 APM 平台，也不在缺少真实判定依据时宣称 Skill 的业务准确率。

### 3.2 角色与使用场景

| 角色 | 主要使用场景 |
| --- | --- |
| 平台管理员 | 管理组织、项目、环境、成员、角色、数据治理策略和运行时接入策略。 |
| Skill 作者 | 导入或创建 Skill，维护元数据，查看版本、问题、评测结果和进化候选。 |
| 质量负责人或发布审批人 | 管理质量标准和评测资产，审核候选版本，决定发布、灰度、下线或回退。 |
| Agent 开发者或使用者 | 从平台搜索和获取已发布 Skill，安装 Skill 与 Tracker，查看本地安装和运行上报状态。 |
| 只读观察者 | 在授权范围内查看资产、版本、运行指标、报告和审计信息，不改变状态。 |

### 3.3 Skill 资产注册、发现与安装

#### REQ-001 资产注册与来源保留

平台应允许有权限的用户注册或导入 Skill，并保留 Skill 的来源类型、来源定位和导入结果。导入内容不可访问、无法读取或缺少必要内容时，导入应失败并说明原因，不得生成可发布版本。

验收：用户能够看到导入成功或失败结果及原因；成功资产能够追溯到来源；必要内容缺失时不能进入发布流程。

#### REQ-002 Skill 内容与元数据管理

平台应识别 Skill 的主描述文件及其附属内容，展示可纳入版本的内容范围，并维护名称、描述、来源、许可信息、依赖和适用运行时等元数据。名称或主描述缺失时，Skill 不得进入发布流程；未知来源不得由平台猜测补全。

验收：资产详情能够展示内容清单和元数据完整性；缺失项和未知项被明确标记。

#### REQ-003 平台 Skill 目录与搜索

用户应能在授权范围内浏览和搜索平台已有 Skill，并按名称、描述、标签、来源、适用运行时、状态和版本筛选。详情页应能查看版本、发布状态、评测结果、安装信息和观测关联信息。

验收：用户能够找到平台已有 Skill，区分不同版本和状态，并进入指定版本详情。

#### REQ-004 已发布 Skill 获取与安装

用户应能选择目标运行时和版本，获取平台中已发布的 Skill，并得到与目标运行时匹配的安装说明或安装入口。草稿、未通过发布门禁或已下线且不可再分发的版本不得作为可安装版本提供。

首批运行时兼容范围按 Witty Skill Insight 的既有方式执行：Codex 支持 CLI 和 VS Code、Cursor、Windsurf IDE 扩展；Claude Code 支持基于 OTLP 的运行数据上报。安装主机支持 Witty 已验证的 Bash 和 PowerShell 路径；未被 Witty 证实的 Claude Code IDE 扩展不纳入首批承诺。具体协议和实现方式在方案阶段确定。

验收：一次获取操作能够明确目标 Skill、版本、运行时和安装结果；不可安装版本会说明阻断原因。

#### REQ-005 Tracker 随 Skill 安装

安装平台 Skill 时，应同时安装或配置对应的 `skill-tracker`，用于收集该 Skill 的运行数据。平台应展示 Tracker 的版本、配置状态、运行时支持状态和最近一次心跳或上报状态。仅安装 Skill 而未完成 Tracker 安装或配置时，不应被标记为完整安装。

验收：安装结果能够分别展示 Skill 和 Tracker 的状态；完整安装记录同时包含二者；Tracker 未完成时可诊断失败原因。

#### REQ-006 安装实例与本地状态

平台应记录 Skill 安装实例对应的 Skill、具体版本、目标 Agent、主机或逻辑实例、运行时、环境、安装时间、当前启用状态和最近健康信息。相同名称但内容不同的版本不得被合并为同一个安装实例。

验收：用户能够查看指定 Agent 或实例当前启用的 Skill 版本、Tracker 状态和最近健康信息。

#### REQ-007 进化版本获取与本地启用切换

当 Skill 形成并发布新版本后，用户应能从平台获取该版本。更新本地 Skill 时，应先识别当前启用版本，保留旧 Skill/Tracker 处于可回退状态，完成新版本和对应 Tracker 的安装、配置及可用性确认后，再停用本地旧 Skill，并启用最新下载的 Skill；平台应记录切换前后版本及结果。新版本未完成可用性确认前不得停用旧版本。

验收：更新成功后，本地同一目标实例中旧版本处于停用状态，最新下载版本处于启用状态；平台可查询版本切换记录。

#### REQ-008 安装、更新与切换异常

Skill 或 Tracker 下载、安装、配置、可用性确认、停用旧版本或启用新版本任一步骤失败时，应保持旧版本继续启用；若旧版本已被停用，则自动回退到此前处于启用状态且可用的 Skill/Tracker 版本，并向 SKILL HUB 上报失败阶段、失败原因、回退结果、切换前后版本和当前状态。若不存在可用旧版本，则不得启用未完成确认的新版本，应标记安装不可用并要求人工处理。回退事件必须进入本地待上报队列，服务恢复后重试并避免重复记账。平台应展示上述状态，不得把未完成切换或回退失败标记为成功；回退本身失败时应标记需要人工处理并持续上报。

验收：更新或安装失败后旧版本保持或恢复启用，失败和回退结果均可在 SKILL HUB 查询；SKILL HUB 暂不可用时，恢复后能够补报且不会产生重复回退记录；回退失败时用户能够识别需要人工处理的状态。

### 3.4 版本、生命周期与发布治理

#### REQ-009 不可变版本与版本差异

每次 Skill 内容变更都应形成独立版本。已创建版本的内容、内容标识、来源和创建信息不得被原地修改；用户应能比较版本的主描述和附属内容差异。

验收：修改已创建版本会产生新版本；任一版本详情能够查看自身内容和与其他版本的差异。

#### REQ-010 生命周期状态

平台至少应区分草稿、候选、已发布、已下线、紧急撤回和已废弃状态，并展示状态变更记录。草稿不可被目标 Agent 安装；候选必须满足发布门禁后才能发布；已下线或已废弃版本不得作为新的默认安装版本。普通下线仅阻断新增安装，已安装实例继续运行并持续上报当前状态，除非后续明确执行更新、卸载或回退。因高危安全问题或高危行为执行紧急撤回时，授权管理员可强制停用存量实例，并记录停用结果和原因。

验收：不同状态对查看、安装和发布的影响清晰可见；已下线版本不能被误当作最新可安装版本；紧急撤回能够阻断新增安装并停用授权范围内的存量实例，停用结果和原因可查询。

#### REQ-011 发布范围与渠道

平台应支持在公司、项目和环境等授权范围内发布 Skill 版本，并明确发布目标、版本、审核状态和发布时间。一个版本可以发布到一个或多个授权范围。

验收：用户能够查询某版本发布到哪些范围，以及每个范围当前使用的版本。

#### REQ-012 发布门禁与审核

发布前平台应沿用 iflytek SkillHub 的治理基线检查安全扫描、静态质量结果、评测结果、审核状态和风险限制：扫描失败不得发布；团队空间发布应完成团队审核；提升至全局或更大授权范围时应完成二次审核；高风险候选不得绕过人工审核。任一必需门禁未满足时应阻止发布，并指出缺失证据或阻断原因。发布、下线、紧急撤回和回退请求应保留发起人、时间、对象、前后状态和原因。

首期默认发布策略如下：

| 策略 | 默认规则 |
| --- | --- |
| 自动发布白名单 | 仅限低风险候选；无高危/严重安全问题、无权限或外部写操作变化、无新运行时兼容性变化，且至少完成 30 个有效评测案例，回归结果和有效评分不低于基线。其他候选必须人工审核。 |
| 自动发布主体 | 白名单候选由 SKILL HUB 自动发布主体执行，不要求虚构人工申请人或审批人；必须记录自动发布主体、命中的白名单规则版本、全部门禁证据和发布时间。人工触发或白名单外候选必须进入审批流程。 |
| 审批人分离 | 人工发布申请人不得审批自己的候选；团队审核人与提升至全局或更大范围的审核人不得为同一人。自动发布主体不得被记录为人工审批人。 |
| 比较基线 | 默认以同一目标范围内当前已发布稳定版本为基线，必须固定运行时、模型、工具环境、任务集和判定器；无法满足相同条件时不得自动扩大灰度或自动全量发布。 |
| 灰度范围 | 默认覆盖符合条件安装实例的 10%，按向上取整计算且至少覆盖 1 个实例；没有符合条件实例时不得进入灰度。 |
| 观察门槛 | 默认观察 24 小时，且灰度范围内至少累计 30 次 Skill 调用后才允许扩大范围。样本不足时保持灰度，不得自动全量发布。 |
| 自动回退 | 灰度期间错误率较基线增加 2 个百分点或在基线大于 0 时相对增加 20%；基线为 0 时灰度错误率达到 2% 即触发；有效评分下降 5 个百分点，或出现高危/严重问题时，自动回退至此前版本并上报。 |

验收：门禁未满足时发布失败；符合白名单的低风险候选可按默认规则自动发布并留下自动发布证据；其他候选受到人工审核和审批人分离约束；系统能识别不可比基线和样本不足状态；灰度扩大、自动回退及状态变更均可追溯。

#### REQ-013 灰度与回退

平台应支持在部分安装实例或部分授权范围内使用候选版本，并能将发布渠道或安装实例切回此前已发布版本。默认灰度范围为符合条件实例的 10%（向上取整且至少 1 个实例），观察期为 24 小时且至少 30 次调用。错误率较基线增加 2 个百分点，或基线大于 0 时相对增加 20%，或基线为 0 时灰度错误率达到 2%，有效评分下降 5 个百分点，或出现高危/严重问题时，应自动回退并将回退原因、结果和运行证据上报 SKILL HUB。灰度和回退过程应保留范围、操作人、原因及期间产生的运行和评测证据。

验收：用户能够识别灰度范围和当前版本，并能查询回退记录及相关证据。

### 3.5 Tracker 与运行观测

#### REQ-014 运行事件采集

`skill-tracker` 应在运行时尽可能采集一次 Agent 任务的可用执行事件，包括任务或会话、Agent、子 Agent、模型、工具、MCP 和 Skill 调用事件。运行时不提供某类事件时，应明确标记能力缺失，不得用推测值填充。

验收：已支持的运行时能够产生可查询的 Skill 运行事件；不支持的事件类型显示为缺失而非虚构。

#### REQ-015 Skill 调用版本归属

可识别的 Skill 调用应关联 Skill、不可变版本标识、调用标识、父事件或 Trace 标识、触发方式和 Tracker 版本。无法可靠归属版本的历史事件应标记为版本未知，不得自动归属到当前最新版本。

验收：用户能够从调用记录确认实际运行版本；归属不完整时可见缺失原因。

#### REQ-016 本地缓冲与上报状态

网络或服务端暂不可用时，Tracker 应保留待上报数据，并在恢复后继续上报。Skill 更新失败、自动回退和紧急撤回等状态事件与运行数据具有同等的待上报和补报要求；重复重试不得重复生成同一状态记录。用户应能查看成功、待上报、失败和丢弃状态，以及被策略拒绝、超限或格式非法的原因。

验收：暂时不可用不会导致状态被伪装为成功；上报恢复后状态可更新。

#### REQ-017 数据最小化与脱敏

Tracker 应遵循 Witty Skill Insight 的数据最小化基线：Codex 默认不读取 `transcript_path`，完整 prompt/transcript 不作为默认采集内容；完整代码片段也不作为平台默认上传项，具体 runtime 适配器如需提供代码内容，必须经过组织策略批准。工具输入输出、FileEdit、Terminal 和摘要内容仅在对应 runtime 适配器暴露且策略允许时采集。上传前递归脱敏 API Key、token、secret、password 等敏感赋值以及本地 Windows、UNC、`/Users/...`、`/home/...` 路径，Token 用量字段保留数值；适用采集器的文本内容最长 2000 字符。实验性可见 transcript 估算只能由用户显式开启，且必须标记为估算，不得充当精确输入输出。

密钥、凭据和明确受保护字段不得作为普通运行内容上传。Witty 用量统计中的“原始事件保留 365 天”不适用于 SKILL HUB 的 Skill 制品、运行证据、报告和审计数据；上述数据按 REQ-026 永久保留。

验收：上传数据受策略控制；受保护字段不会按普通 Trace 内容上传；用户能够识别被脱敏或拒绝的数据。

#### REQ-018 双向追踪与证据链

平台应从同一组运行事件提供 Agent 执行链路视图和 Skill 调用轨迹视图，并支持在二者之间双向查看。指标、问题归因、评测结论和发布决策应能关联到原始 Trace、Skill 版本、Tracker 版本和采集时间；关联缺失时展示缺失原因，不构造调用树。

验收：用户能够从一次 Skill 调用定位到关联 Agent 链路，也能从 Agent 链路定位到 Skill 调用及其版本。

#### REQ-019 指标、比较与异常

平台应支持按 Skill、版本、运行时、模型、任务标签、项目、环境和时间窗口查看调用量、判定通过率、可用时的准确率、Token、成本、延迟、错误率、触发率和判定覆盖率等指标。首批评测沿用 Witty 的 LLM Judge 结构化评分；有效评分定义为人工修正分优先于机器评分，未完成人工修正时使用机器评分。业务回执和脚本断言未在当前 Witty 口径中定义为更高优先级真值，不得自行混入同一指标。

每项指标应展示数据范围、时间范围、分子、分母和计算条件；缺少维度或真实判定依据时不得参与比较或显示为准确率。

验收：指标定义和数据缺失状态可见；比较条件不一致或样本不足时，结果被标记为不可直接比较。

### 3.6 评测与 Skill 自进化

#### REQ-020 评测资产与多运行时评测

平台应管理可独立版本化的评测套件、案例、数据集、判定器、运行配置和报告，并支持在已支持的运行时、模型和环境中对指定 Skill 版本执行相同评测。每次评测应记录 Skill 版本、评测资产版本、运行时、模型、环境和执行时间。

验收：评测结果能够关联到明确的 Skill 版本和评测条件；不同运行条件的结果不会被无条件混合。

#### REQ-021 静态质量检查与问题归因

平台应支持对 Skill 版本执行可配置的静态质量检查，并记录规则标识、严重程度、证据、说明和修复建议。平台应区分静态检查问题、评测失败、运行失败、模型异常、工具异常和采集异常等问题来源；自动归因应展示证据和置信边界，用户可以补充人工归因。

验收：质量问题能够定位到规则和证据，并能区分不同问题来源。

#### REQ-022 进化候选版本

平台可基于用户反馈、已确认问题或评测结果形成 Skill 进化候选。候选必须标明基线版本、内容差异、来源证据、生成时间和状态，不能直接覆盖已发布版本。

验收：用户能够查看候选相对基线的变化和依据；候选与已发布版本相互独立。

#### REQ-023 复测、审核与进化发布

进化候选在发布前应能够执行适用的静态检查、回归案例和评测，并展示相对基线的变化。涉及权限变化、外部写操作、质量下降、新运行时兼容性变化或高风险标记的候选，应进入人工审核；团队范围向更大范围提升时应执行二次审核。自动生成候选或自动执行验证不等同于自动发布，当前不允许高风险候选自动发布。

验收：候选发布前具备可查询的复测和审核证据；高风险候选不会绕过人工审核。

### 3.7 组织治理、权限与审计

#### REQ-024 授权范围隔离

平台应在公司、项目和环境等授权范围内隔离 Skill、版本、安装实例、Trace、评测资产、报告和凭据。用户只能访问其被授权范围内的数据和操作。

验收：越权用户无法查看或操作未授权范围的资产和数据。

#### REQ-025 角色权限控制

平台应按角色控制导入、版本创建、发布、下线、紧急撤回、安装、运行数据查看、评测执行、进化、审核和治理配置等操作。应支持 iflytek 采用的空间 Owner/Admin/Member 分级治理和团队审核、全局提升二次审核模式。发布申请人与审批人必须分离；团队审核人与提升至全局或更大范围的审核人不得重复；自动发布主体不得充当人工审批人。

验收：不同角色的可操作范围清晰且经过权限校验；关键操作不会由只读角色执行。

#### REQ-026 数据保留与删除

Skill 制品、运行证据、评测和分析报告、发布及操作审计数据必须永久保留，不设置自动过期、普通删除或按公司/项目/环境缩短保留期限的策略。平台不提供针对上述数据的普通删除权限；任何删除请求如被受理，必须拒绝并记录请求人、时间、对象和拒绝原因。

验收：授权用户能够持续查询 Skill 制品、运行证据、报告和审计数据；系统不会因到期策略自动删除，不提供普通删除权限，删除请求能够被拒绝并审计。

## 5. 非目标

- 不替代 Agent runtime，也不负责实现 Agent 本身的任务执行。
- 不替代通用日志、APM 或公司统一观测平台。
- 不把评测通过率、用户反馈通过率或模型判定结果直接称为业务准确率。
- 不在缺少明确策略、评测和人工审核要求时自动覆盖生产版本或自动发布高风险版本。
- 不在本需求阶段规定具体技术架构、接口字段、数据表、部署方式或开发任务。
