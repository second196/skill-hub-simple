本文件是治理控制台的架构基线，不是现有页面或组件清单。当前仓库没有前端源码、构建文件、路由或测试入口。

## 2. 架构目标与边界

### 2.1 架构目标

- 使用 Vue 建设 Skill 资产登记、目录、版本、发布门禁、范围、策略和审计控制台。
- 让用户能区分版本和生命周期状态，并能查看来源、门禁证据、发布范围和审计关联。
- 将权限、加载、空数据、错误、部分成功和撤回状态作为显式界面状态。
- 将领域数据和 API 契约集中在 Feature 模块，避免页面之间复制业务规则。
- 保证治理操作有明确的确认、结果反馈和审计关联，不在前端绕过后端授权和门禁。

### 2.2 前端负责范围

```text
资产登记/导入结果、完整性详情、目录搜索和版本差异
生命周期和发布范围查询、门禁证据和发布决策查看
发布/下线/紧急撤回申请、策略查看与授权配置入口
审计查询、失败原因、部分范围结果和操作结果呈现
```

### 2.3 前端不负责范围

- 不在浏览器执行 Skill、评测、扫描、灰度流量或版本回退。
- 不将前端校验当作权限、门禁、版本不可变和审计的最终依据。
- 不采集完整 transcript、prompt、代码片段或敏感运行内容。
- 不把安装、运行观测和评测 Feature 的页面状态复制为本 Feature 的领域状态。

## 3. 应用结构和页面边界

推荐按“应用壳 + Feature 模块”组织：

- 应用壳负责启动、全局身份、路由、布局、错误边界和基础主题。
- `asset-governance` Feature 负责资产、版本、目录、发布、策略和审计页面。
- 下游 Feature 通过 API/事件契约接入，不共享内部 store、组件状态或后端领域模型。
- 权限和范围由后端返回最终结果；前端只负责隐藏不可用入口、展示拒绝原因和处理过期权限。

## 4. 前端目录结构

以下为拟创建的 greenfield 目录结构，遵循 Vue 3 + TypeScript + Vite + Vue Router + Pinia 参考基线。iflytek SkillHub 使用 React 19 控制台，本产品保留 Vue 3 以遵循已确认的前端选型；认证、可观测性和部署边界参考 iflytek 的企业私有化实践。

```text
frontend/
├─ package.json
├─ vite.config.ts
├─ tsconfig.json
├─ public/
├─ src/
│  ├─ main.ts                                      # 应用启动入口
│  ├─ app/                                         # 应用启动、全局注册和插件装配
│  ├─ router/                                      # 路由、守卫和路由元信息
│  ├─ stores/                                      # 跨页面/模块共享状态
│  ├─ pages/                                       # 路由页面入口
│  ├─ modules/                                     # 按业务域组织的模块
│  │  └─ asset-governance/
│  │     ├─ api/                                   # Feature API 请求和响应映射
│  │     ├─ components/                            # Feature 业务组件
│  │     ├─ composables/                           # Feature 组合式逻辑
│  │     ├─ services/                              # Feature 流程编排
│  │     ├─ types/                                 # Feature 类型
│  │     └─ tests/                                 # Feature 测试
│  ├─ components/                                  # 跨页面公共组件
│  ├─ composables/                                 # 跨模块组合式逻辑
│  ├─ services/                                    # 公共服务编排
│  ├─ api/                                         # 请求封装和响应映射
│  ├─ utils/                                       # 无业务语义工具
│  ├─ types/                                       # 跨模块稳定类型
│  └─ assets/                                      # 图片、图标、字体等资源
├─ tests/
│  ├─ unit/                                        # 单元和组件测试
│  ├─ integration/                                 # 页面与 API 集成测试
│  ├─ contract/                                    # 前后端契约测试
│  └─ e2e/                                         # 关键治理流程端到端测试
└─ docs/                                           # 前端局部设计和运行说明
```

目录约束：页面只负责组合和用户交互；API 映射不把后端 DTO 直接扩散到页面；业务判断放在 Feature model/composable 或后端；通用组件不能反向依赖 Feature；全局 store 不能成为任意页面数据的共享垃圾桶。

## 5. 路由、状态和数据请求

### 5.1 页面路由

路由至少按以下用户目标划分：资产目录、资产详情、版本详情/差异、发布范围、发布门禁与决策、治理策略、审计查询。具体路由名称待产品导航确认。

路由守卫只做服务端会话登录态、角色和范围能力的预检查；后端每次关键操作仍必须重新授权。直接访问无权页面时展示统一拒绝状态，不泄露资产名称、版本或审计内容。

### 5.2 状态模型

异步请求统一表达 `idle`、`loading`、`success`、`empty`、`partial`、`error` 和 `forbidden`。发布、下线和紧急撤回等写操作还必须表达请求中、成功、失败、重复请求和逐范围结果。

Skill 生命周期状态使用后端返回的枚举和状态说明，不在前端猜测“最新可安装版本”。`draft`、`candidate`、`published`、`offline`、`emergency_revoked` 和 `deprecated` 的展示、操作入口和提示必须由后端能力结果驱动。

### 5.3 数据请求

- API 客户端集中处理请求 ID、鉴权、超时、错误码和重试边界。
- 查询可缓存，但发布状态、权限和当前范围版本必须支持刷新和失效处理。
- 写操作采用幂等请求标识，重复提交显示原结果，不重复触发前端状态变更。
- 列表分页、筛选条件、时间范围和空结果必须可复现并可分享；具体分页协议待确认。
- 前端不上传完整 transcript、prompt、代码片段或未经策略允许的敏感内容。

## 6. 组件和交互约束

- 资产、版本、范围、证据和审计使用适合扫描和比较的表格、筛选、详情和时间线布局；具体组件库待确认。
- 高风险发布、紧急撤回、策略缩短保留期等操作必须显示目标范围、版本摘要、影响说明和二次确认。
- 门禁结果展示每个必需证据、结果、缺失原因、策略版本和生效范围；不能只显示一个笼统的“发布失败”。
- 多范围操作展示逐范围成功、失败和未执行结果，避免把部分成功渲染成整体成功。
- 所有关键操作同时提供键盘可达的焦点顺序、可读标签、状态文字和错误关联。
- 颜色不是唯一状态表达方式；状态徽标、图标和文本需同时表达含义，并遵守组织无障碍标准。
- 加载、空数据、错误、无权限、过期数据和撤回状态不能互相覆盖或显示为普通空列表。

## 7. 权限、安全与隐私

- 前端显示的操作按钮由后端授权能力和目标范围共同决定，但按钮隐藏不替代后端鉴权。
- 登录页面只支持账户密码登录；会话由后端创建并通过 HttpOnly/Secure/SameSite Cookie 维护。
- 审计详情、来源定位、依赖、制品和门禁报告按返回范围控制；错误消息不得回显密钥、凭据、内部路径或完整制品内容。
- 发布申请和人工审批页面必须显示申请主体、审批主体、机器/人工主体类型和审计关联。
- 运行观测、安装和评测页面若由其他 Feature 提供，使用其公开契约和权限结果，不读取其内部状态。
- 前端配置不保存长期密钥；会话管理、跨站请求防护和内容安全策略由后端/部署基线共同确认。

## 8. 性能、兼容性和可观测性

当前没有确认的首屏、交互延迟、并发用户、数据规模或浏览器版本指标，不自行补充数值。实施时至少应验证：

- 目录列表和审计查询使用分页、筛选和按需加载，避免一次加载全部报告和制品。
- 版本差异和门禁报告在大内容时采用分段或按需加载，不阻塞整个页面。
- 前端错误上报关联路由、请求 ID、用户作用域（脱敏）、对象 ID 和版本摘要，不上传敏感正文。
- 平台前端观测与用户 Agent 运行观测分开，不能用前端访问量替代 Skill 调用量。
- 浏览器兼容、国际化、主题和离线行为待产品与工程基线确认。

## 9. 构建、测试、发布和回滚

### 9.1 测试层级

- 单元测试覆盖状态映射、权限展示、表单校验、错误转换和关键 composable。
- 集成测试覆盖目录筛选、版本差异、门禁证据、逐范围结果和策略生效时间。
- 契约测试固定前后端字段、状态枚举、错误码、`version_digest` 和审计关联。
- 端到端测试覆盖导入结果、版本查看、门禁阻断、发布申请、紧急撤回和越权访问。
- 测试数据不得包含真实凭据、完整 prompt、代码片段或真实敏感制品。

### 9.2 构建和发布

构建工具、包管理器、静态检查、组件库、测试命令和环境变量待确认；部署编排采用 Docker Compose 2.24.6，生产环境采用 Kubernetes 1.28.15 和 Helm 3.14.4。前端发布必须使用可回退的构建产物；API 契约不兼容时先兼容后切换，不能要求旧页面立即理解新状态。

### 9.3 回滚

- 页面构建发布失败时恢复上一构建产物。
- API 兼容问题通过兼容字段或恢复上一前端版本处理，不在前端伪造缺失数据。
- 权限、门禁和保留策略的回滚由后端策略版本负责，前端显示实际生效版本和回滚结果。
- 新页面功能未获得后端能力时保持禁用或只读，不把前端入口作为已发布能力。

## 10. 待确认项与维护要求

- Vue 版本、是否使用 TypeScript、构建工具、包管理器、组件库和状态管理方案。
- 路由、登录态、组织范围、权限模型和后端 API 契约。
- 浏览器兼容、无障碍、性能、国际化和发布平台标准。
- 前端实施标准入口及其格式化、静态检查、测试和评审要求。

本基线由 `product-development` 维护。框架、目录边界、公共组件或构建发布约束发生变化时必须升级基线版本，并同步检查引用它的设计、实施计划和 Feature 状态。
