# 功能需求文档规范

本文档定义功能开发包中的 `requirement.md` 应该如何编写。

本规范适用于所有 feature 需求文档。这里的 `feature` 是研发闭环单元，可以是业务功能，也可以是技术改造、机制治理、性能优化或专项修复。无论需求来自既有资料整理、产品规划、交付项目还是后续新增编制，单个 `feature` 都应在 `docs/product-development/features/feature-<featureId>/requirement.md` 中形成稳定的需求文档，作为后续方案、实现和测试设计输入。

功能需求文档只描述需求本身，不描述技术实现方案、接口设计、测试用例或开发计划。需求内容应基于明确来源编写，来源未说明的信息不得由 AI 推断补齐。

---

## 1. 适用对象

本规范适用于以下文档：

- `docs/product-development/features/feature-<featureId>/requirement.md`
- 从既有需求资料整理出来的单个功能需求文档
- 后续新增需求直接编制的单个功能需求文档
- 可作为技术方案、开发任务和测试设计输入的需求文档

本规范不适用于以下文档：

- 需求来源资料的转写稿、纪要或附件
- 功能清单总览页
- 技术方案、接口设计、测试用例或开发计划
- 面向用户的操作手册

---

## 2. 文档定位

单个 feature 需求文档必须围绕一个完整可交付的 `feature` 编写。

“完整可交付”指该需求可以被独立理解、独立评审、独立进入技术方案和开发任务拆解。文档颗粒度取决于 `feature` 复杂度：简单 `feature` 可以只有少量章节；复杂 `feature` 可以在“功能描述”中继续拆分多个小节，但不应把一个互不相关的需求集合塞进同一篇文档。

feature 需求文档必须回答以下问题：

1. 需求来自什么来源，为什么要做这个 `feature`。
2. 这个 `feature` 要解决什么问题，影响哪些用户、研发角色或系统对象。
3. 这个 `feature` 包含哪些流程、规则、约束、链路或边界变化。
4. 这个 `feature` 有哪些非功能性要求，例如异常处理、性能、安全或兼容性。
5. 这个需求经历过哪些版本修订和需求评审。

---

## 3. 文件命名与标题

### 3.1 文件命名

功能需求文档文件名固定为：

```text
requirement.md
```

示例：

```text
docs/product-development/features/feature-WEBCAPP-10234/requirement.md
docs/product-development/features/feature-jira-keyword/requirement.md
```

功能标识写在父目录 `feature-<featureId>/` 中，`requirement.md` 不再重复功能标识。

### 3.2 正文标题

正文一级标题使用中文功能名称，不包含 `feature-` 前缀。

示例：

```markdown
# 加密卡授权
```

---

## 4. Frontmatter

每个功能需求文档必须包含基础 frontmatter，只保留文档治理必需字段。

模板：

```yaml
---
title: 加密卡授权
description: 加密卡授权功能需求
audience:
  - product-development
owner: product-development
status: draft
lastReviewed: 2026-05-31
sourceType: manual
---
```

字段要求：

| 字段           | 是否必填 | 填写规则                                                               |
| -------------- | -------- | ---------------------------------------------------------------------- |
| `title`        | 必填     | 与正文一级标题一致                                                     |
| `description`  | 必填     | 简要说明当前功能需求                                                   |
| `audience`     | 必填     | 默认包含 `product-development`                                         |
| `owner`        | 必填     | 需求或产品责任域；未明确时使用 `product-development`                   |
| `status`       | 必填     | 草稿使用 `draft`，当前有效需求使用 `active`，废弃需求使用 `deprecated` |
| `lastReviewed` | 必填     | 最近一次文档检查日期，使用 `YYYY-MM-DD`                                |
| `sourceType`   | 必填     | 手工编制或整理的功能需求文档使用 `manual`                              |

需求来源、项目名称、产品版本、评审记录等信息写入正文，不写入 frontmatter。

---

## 5. 标准章节结构

单个功能需求文档默认采用以下结构：

```markdown
# <功能名称>

## 1. 版本修订记录

## 2. 需求来源

## 3. 功能描述

## 4. 非功能性需求

## 5. 需求评审记录
```

可选章节根据需求复杂度增加：

```markdown
## 6. 数据与字段
```

章节使用规则：

- `版本修订记录` 必须放在文档最上头；除 frontmatter 和一级标题外，它必须是正文第一块内容。
- `需求来源`、`功能描述`、`非功能性需求`、`需求评审记录` 为必填章节。
- `数据与字段`、`权限与角色`、`依赖与关联功能` 为可选章节，只有当前功能确实涉及时才单独展开。
- 界面与交互默认并入 `功能描述`，不作为固定独立章节。
- 如果某个必填章节当前没有内容，应说明“暂无”或“来源未明确”，不要删除章节。

---

## 6. 章节填写规则

### 6.1 版本修订记录

本节记录当前功能需求文档的版本变化，必须放在文档最上头。除 frontmatter 和一级标题外，本节必须是正文第一块内容。

推荐表格：

```markdown
| 版本 | 日期       | 修订人 | 修订说明 |
| ---- | ---------- | ------ | -------- |
| v0.1 | 2026-05-28 |        | 初稿     |
```

填写要求：

- 每次影响需求含义的修改都应新增一条记录。
- 只修改错别字、格式或链接时，可以不新增版本。
- 修订说明应描述需求变化，不写技术实现变化。

### 6.2 需求来源

本节用一句话说明需求来自什么来源。

推荐结构：

```markdown
项目：JLJJ、TFQD。

自主规划：KMCAPP CLOUD V1.7.0。
```

以上示例按实际来源二选一填写。

填写要求：

- 需求来源只保留一句话，不使用表格。
- 如果来源是项目，标识项目名称。
- 如果来源是自主规划，标识产品版本号。
- 项目名称或产品版本号不明确时，应写“来源未明确”，不得由 AI 推断补齐。

### 6.3 功能描述

本节是 feature 需求文档的主体，用于详细说明功能清单、业务流程、界面交互、规则、约束或技术边界变化。

功能描述不强制固定小节。编写者应根据功能复杂度组织内容，常见小节包括：

- 功能目标
- 使用场景
- 操作入口
- 操作流程
- 页面、弹窗、按钮、菜单和提示
- 业务规则
- 状态变化
- 输入输出
- 异常场景
- 边界条件

填写要求：

- 一个 feature 需求文档应描述一个完整可交付的 `feature`。
- 简单 `feature` 可以用少量段落和列表说明。
- 复杂 `feature` 可以继续拆成 `3.1`、`3.2`、`3.3` 等小节。
- 界面与交互优先并入相关流程或场景中描述，避免把同一件事拆到多个章节重复维护。
- 描述应尽量使用需求语言，不写技术实现、组件选型、接口字段映射或代码结构。
- 来源未明确的信息，应写“来源未明确”，不得由 AI 推断补齐。

### 6.4 非功能性需求

本节记录当前功能相关的非功能性要求。

非功能性需求包括但不限于：

- 异常处理
- 性能要求
- 安全要求
- 权限安全边界
- 数据量要求
- 兼容性要求
- 可用性要求
- 审计或日志要求

推荐表格：

```markdown
| 类型     | 要求 | 说明 |
| -------- | ---- | ---- |
| 异常处理 |      |      |
| 性能要求 |      |      |
```

填写要求：

- 有明确要求时，写清要求和约束。
- 没有明确要求时，填写“暂无明确非功能性需求”。
- 异常处理如果和具体流程强相关，可以在 `功能描述` 中说明，并在本节汇总关键要求。

### 6.5 需求评审记录

本节只记录人工评审记录，不记录 AI 或自动化工具自己的生成、检查、修订行为。

推荐写法：

```markdown
暂无人工评审记录。
```

如已经发生人工评审，推荐表格：

```markdown
| 日期 | 评审人 | 结论 | 说明 |
| ---- | ------ | ---- | ---- |
```

填写要求：

- 只记录真实发生的人工评审。
- 没有人工评审时，写“暂无人工评审记录”。
- AI 生成、AI 修改、自动化检查不作为需求评审记录。

## 7. 可选章节

### 7.1 数据与字段

当功能涉及明确的数据对象、字段、输入输出、默认值或校验要求时，应增加本节。

推荐表格：

```markdown
| 字段 | 含义 | 类型或格式 | 必填 | 默认值 | 校验规则 | 说明 |
| ---- | ---- | ---------- | ---- | ------ | -------- | ---- |
```

如果字段只服务于某个具体流程，也可以直接写在 `功能描述` 的对应小节中，不必单独成章。

如果当前需求没有明确的数据对象、字段、输入输出、默认值或校验要求，不写 `数据与字段` 章节。

## 8. AI 填写约束

AI 生成或更新功能需求文档时必须遵守：

1. 只整理需求来源中已经表达的内容。
2. 不得补写来源没有的业务规则、异常、字段约束、权限或非功能指标。
3. 不得写技术实现方案、组件设计、接口设计、测试用例或开发任务。
4. 来源缺失的信息必须写“来源未明确”或“暂无明确要求”。
5. 需求评审记录只记录真实发生的人工评审；没有人工评审时写“暂无人工评审记录”，AI 不得把自己的生成、修改或检查写入评审记录。

---

## 9. 单个功能文档验收标准

一个功能需求文档要被视为合格，至少满足以下条件：

- 文件路径符合 `docs/product-development/features/feature-<featureId>/requirement.md`。
- frontmatter 字段完整，不包含额外的 `requirement` 扩展块。
- 正文包含版本修订记录、需求来源、功能描述、非功能性需求和需求评审记录。
- 需求来源明确区分项目或自主规划。
- 项目需求填写项目名称，自主规划需求填写产品版本号。
- 功能描述能支撑一个完整可交付功能的理解和后续拆解。
- 可选章节仅在确有需要时出现；没有明确数据与字段要求时，不写 `数据与字段` 章节。
- 文档不包含技术实现、接口设计、测试设计或开发计划。
