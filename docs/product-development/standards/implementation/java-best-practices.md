# Java 开发最佳实践

本文面向产品开发人员，用于约束 Java 代码在类型设计、实现方式和公共契约维护上的一致性。

> 规范依据：《阿里巴巴 Java 开发手册》。组织批准的手册具体版本待确认；在版本确认前，本文件只作为实现检查清单，不宣称完成手册合规认证。

## 0. SKILL HUB 适用约束

- 使用 JDK 8、Spring Boot 2.7.18 模块化单体、Spring MVC 5.3.31、Spring Security 5.7.11、MyBatis-Plus 3.5.5 和 Maven 3.8.8；版本选择必须保持 Java 8 兼容。
- 平台认证仅使用账户密码登录和服务端会话；密码使用 BCrypt 哈希保存。
- 遵循 `controller -> service -> mapper` 的依赖方向，DO、DTO、VO 和 Query 不混用。
- 资产版本、发布策略、门禁决策和审计对象的不可变性由 Service 事务和数据库约束共同保证。
- 数据库、迁移、索引和保留规则遵循 [SKILL HUB 数据库设计规范](./database-design.md)。

## 1. 基本原则

- 优先表达业务语义，不优先追求技巧性写法。
- 优先使用明确类型和明确返回值。
- 领域对象、DTO、VO 和持久化对象要分清边界。
- 公共 API 要稳定、可读、可演进。
- 异常、校验和日志要形成一致的处理方式。

## 2. 类型与对象

### 2.1 优先使用明确模型

- 用有意义的对象承载业务数据，不要长期堆叠原始 `String`、`Map`、`Object`。
- 值对象、枚举、专用包装类型优先于模糊字段。
- 必要时为标识、状态、金额、时间建立清晰模型。

### 2.2 DTO 和领域对象分离

- 请求对象、响应对象和领域对象不要混用。
- 持久化模型不要直接暴露给上层调用方。
- 传输结构变更不要直接冲击核心业务模型。

## 3. 方法与返回值

### 3.1 一个方法只做一件事

- 方法职责要单一。
- 读取、校验、转换、持久化、副作用尽量拆开。
- 复杂流程优先拆成可测试的小方法。

### 3.2 返回值要有语义

- 能明确返回结果对象时，不要只返回 `boolean`。
- 多结果场景优先返回结构化对象或枚举结果。
- 空值语义要明确，避免靠调用方猜测。

## 4. 异常处理

### 4.1 异常要分层

- 参数校验失败、业务失败、系统失败要区分。
- 不要吞掉异常。
- 不要用异常表达正常业务分支。

### 4.2 异常信息要可定位

- 错误消息要包含必要上下文。
- 公共接口抛出的异常类型要稳定。
- 记录日志时要保留关键业务标识。

## 5. 分层与依赖

### 5.1 分层边界清晰

- Controller、Service、Domain、Repository 职责要清楚。
- 不要让控制层堆业务逻辑。
- 不要让持久层承担复杂业务判断。

### 5.2 依赖方向稳定

- 上层依赖下层，不要反向耦合。
- 公共能力放到稳定的公共模块。
- 不要为了临时复用把内部实现暴露成公共 API。

## 6. 集合与空值

- 集合返回尽量避免 `null`，优先返回空集合。
- 判空逻辑集中处理，不要重复散落。
- 对外输入要先校验，再进入核心逻辑。

## 7. 代码风格

- 命名要准确、统一、可读。
- 布尔字段避免歧义命名。
- 常量、枚举、配置项命名保持一致。
- 复杂逻辑优先抽取方法，不要堆叠嵌套。

## 8. 开发检查

- 类型是否表达了真实业务语义。
- 异常是否分层、是否可定位。
- 返回值是否明确。
- 分层边界是否清晰。
- 是否存在可拆分的长方法或重复逻辑。
